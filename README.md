# 管风琴调音排程台

给管风琴维护组使用的排程与调音记录台（React + Vite + TypeScript）。
一台移动风机轮送到各个场馆，簧片管必须在当地湿度里稳定足够时长才能定音；
两名调音师的实测冲突逐字段确认；报告只按最终值重算异常标记。

## 功能页

| 页面 | 内容 |
| --- | --- |
| 场馆与音管 | 场馆、音栓、音管编号、分组、音高、簧片状态、定音风量(CFM)、维修备注登记与筛选台账 |
| 风机与温湿度 | 风机轮送到场馆（送达即开启单次维护、稳定计时起点）、启动/模拟故障/恢复；温湿度登记与历史；事件日志 |
| 排程时段 | 同时段风量叠加 vs 风机容量实时校验；簧片最早可排时间；预留开始/完成/失效状态 |
| 实测与冲突 | 调音师提交实测；第二份同管实测挂为冲突版本，字段差异表逐字段取“先到/后到” |
| 单次维护报告 | 每次按最终值重算异常标记（音分超限、簧片异常、稳定不足、湿度失效、缺实测、冲突未决） |

## 关键业务规则

1. **风机容量 + 稳定时长同时约束排程**（`src/domain/schedule.ts`）
   - 同时段所有进行中预留的 CFM 之和不得超过风机容量（恰好等于允许）。
   - 簧片管开始时间必须晚于「风机送达时间 + 稳定分钟数」（默认 60 分钟，可在报告页调整）。
   - 风机不在该场馆或未运转（含启动失败）时不能排时段。
   - 同一根音管不能重复预留。
2. **冲突不覆盖先到值**（`src/domain/measurements.ts`）
   - 同一音管/同一次维护：第一份为「先到实测」；第二份原样保留为「冲突待确认」，先到那份一个字段都不改。
   - 冲突未确认前拒绝更多提交；差异表逐字段（音高、音分、温湿度、簧片状态、备注）选择取值后，合并生成独立的「最终确认值」。
   - 先到记录保持 `original`、后到记录归档 `archived_conflict`，全程可追溯。
3. **关机 / 风机故障恢复**
   - 关机期间禁止改排程与提交实测；所有数据保存在本机 `localStorage`（并可导出/导入 JSON 备份）。
   - 风机可“模拟启动失败 → 恢复”，恢复后原有预留与实测不变，继续补未完成的部分。
4. **湿度变化使原预留失效**（`src/domain/environment.ts`）
   - 新温湿度与该场馆上一条相比，波动超过阈值（默认 ±10%RH）时，该场馆未关闭维护下所有 `held/in_progress` 预留转为 `invalidated`，需重排；其他场馆不受影响。
5. **报告按最终值重算**（`src/domain/report.ts`）
   - 有冲突 → 取逐字段确认的最终确认值；无冲突 → 先到实测即为最终值；冲突待确认 → 不产出最终值并标异常。
   - 每次打开/点击重算/调阈值都重新计算标记，不修改原始记录。

## 数据存储

仅保存在运行浏览器的本机 `localStorage`（键 `organ-scheduler-v1`）。
首次打开载入一份演示数据（圣玛丽教堂秋季维护，含湿度失效预留与一条双人冲突），
顶栏可用「演示数据」重置、「导出备份 / 导入备份」迁移、「清空」重置。

## 开发

```bash
npm install
npm run dev        # http://localhost:62005
npm test           # vitest，21 个领域规则测试
npm run build      # tsc --noEmit + vite build
```

业务规则全部集中在 `src/domain/` 的纯函数中，UI（`src/components/`）不直接实现规则，
测试覆盖容量叠加、稳定时长、湿度失效、冲突留痕/逐字段确认、关机恢复、报告重算等场景。
